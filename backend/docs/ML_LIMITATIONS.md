# ML limitations — read this before trusting any risk score

BHUSURAKSHA AI has exactly ONE real, trained ML model as of Phase 21: a
**landslide SUSCEPTIBILITY model**, trained on real data, but scoped to a
two-state pilot area (Uttarakhand + Himachal Pradesh) — not India-wide, and
not a validated forecast. Every zone-level risk score (`/predict-risk`,
the Dashboard, Risk Map, Alerts) is still the Phase 1 rule-based engine —
the susceptibility model is served separately at `GET /susceptibility` and
has never been wired into zone-level risk. This document exists so neither
fact is ever lost in a demo, a screenshot, or a stakeholder conversation.

## What actually exists today

- **The Phase 2 synthetic demo model has been retired (Phase 19).**
  `ml/artifacts/landslide_model.joblib` and `model_metadata.json`, plus
  the synthetic training data that produced them
  (`backend/data/raw/demo/landslide_training_data.csv`,
  `data/processed/landslide_training_data_processed.csv`), have been
  deleted. `ml/predict.is_model_available()` now always returns `False`,
  so `POST /predict-risk` and every risk recomputation always report
  `prediction_source: "rule_based_fallback"` — never silently, always
  disclosed in the response.
- The code that *could* train a model
  (`ml/train_model.py`/`ml/preprocessing.py`/`ml/evaluate.py`,
  `data/generate_dataset.py`) is left in place as infrastructure, but
  running it now has nothing to train on — this is intentional, not an
  oversight.
- **Why not simply retrain on the real NASA Global Landslide Catalog data
  ingested in Phase 18 instead?** Because every real `LandslideEvent` row
  has `risk_level` left `null` — Phase 3 through Phase 18 all deliberately
  never fabricate one. A landslide catalog only records *that and where
  an event happened*; it has no negative examples (non-landslide
  locations/times) and no rainfall/terrain/vegetation features joined to
  each event (Phase 11-13's real data sources are still unconfigured — see
  `GET /data-status`). There is currently no scientifically valid way to
  turn this into a supervised classification training set without
  inventing labels or negative samples. **Phase 15 remains explicitly
  stopped for this exact reason** — see below.
- Historically (Phase 2, now retired): a `RandomForestClassifier`
  (`n_estimators=200`, `max_depth=8`) was trained on 600 synthetic rows
  generated by `data/generate_dataset.py` from a hand-written formula, and
  scored a meaningless 100% test accuracy (it was learning its own
  generating function, `app/services/risk_service.calculate_risk`, not
  anything about real landslides). Kept here only as historical context
  for why that model was never something to trust.

## Phase 20/21 — real susceptibility model (Uttarakhand + Himachal Pradesh pilot)

`app/services/negative_sampling_service.py` (real-coordinate pseudo-absence
generation — buffer exclusion around real events, real state-boundary
filtering, stratified against the real study-area terrain distribution),
`scripts/build_susceptibility_dataset.py` (assembles real positives +
generated negatives via Phase 14's `build_feature_vector()`), and
`ml/susceptibility/` (time-based split, PR-AUC/ROC-AUC/precision/recall, a
historical-density ablation) now back a genuinely trained model, using:

- **DEM**: Copernicus DEM GLO-30 (AWS Open Data), mosaicked from 32/42
  1°×1° tiles covering the pilot bbox (10 tiles failed to download —
  transient DNS errors, not retried further; those areas honestly report
  `terrain_available: false`, never an interpolated/fabricated value).
- **Land cover**: ESA WorldCover 10m 2021 v200 (AWS Open Data), full 9/9
  tile mosaic.
- **Rainfall**: real IMD (India Meteorological Department) 0.25° gridded
  daily rainfall (`https://imdpune.gov.in/cmpg/Griddata/Rainfall_25_NetCDF.html`,
  a public form, no login) — extracted only at the exact coordinates/dates
  the real events and generated negatives actually need (58,016 rows), not
  the full national grid.
- **Boundary**: Natural Earth's public-domain India admin-1 states/UTs
  file, used to restrict negative sampling to the real Uttarakhand/Himachal
  Pradesh polygons (never the raw bounding rectangle, which would leak into
  Punjab/UP/Tibet at the corners).

**Real training result** (`ml/susceptibility/artifacts/susceptibility_model_metadata.json`):
1,782 rows (399 real positive events + 1,383 generated negatives, time-based
split at 2015-08-03), **PR-AUC 0.805, ROC-AUC 0.946**, positive-class
precision 0.72 / recall 0.81. The historical-density ablation (same split,
that one feature removed) still scores **PR-AUC 0.67** — the model has real
skill from terrain/rainfall alone, not just "distance to a known event."
Verified live: `GET /susceptibility` at a real training-set event coordinate
scores 97.9/100; at a real negative-sample coordinate (winter, dry,
high-altitude) scores 1.0/100.

**What this is not**: not India-wide (two states only — see `GET
/susceptibility`'s `feature_vector.terrain_available`/`rainfall_available`,
which honestly go `false` outside the pilot's real data coverage), not
wired into `/predict-risk` or any zone's risk_score (a separate, later,
deliberately-unstarted integration — see `app/routes/risk.py`), and not
a "validated forecast" — see the susceptibility-vs-forecast framing above.
Two real bugs were found and fixed while building this: `get_terrain_features`/
`get_landcover` were reading an entire raster band into memory on every
single point query (a real, severe performance bug for any large real DEM,
now fixed to windowed single/3×3-pixel reads) and the dataset builder's
"critical feature" check only checked `rainfall_available` (whether ANY
station was near) rather than each specific rainfall window (a row could
pass the check with a null `rainfall_24h` if only its 30-day window had
data) — both fixed and the dataset/model rebuilt clean.

## What does NOT exist

- **No zone-level risk score** (`/predict-risk`, Dashboard, Risk Map,
  Alerts) is ML-derived. All of those still run the Phase 1 rule-based
  engine only — the Phase 21 susceptibility model is served exclusively at
  `GET /susceptibility` and was deliberately never wired into zone risk
  (see Phase 20's plan notes on why that's a separate, later decision).
- **No India-wide coverage.** The susceptibility model only has real
  DEM/land-cover/rainfall data for the Uttarakhand + Himachal Pradesh pilot
  bbox. Outside it, `GET /susceptibility` honestly reports
  `model_available: true` but a `null` score with an explicit message —
  never a guess.
- **No claim of "validated" or "production-grade" prediction accuracy.**
  PR-AUC 0.805 / ROC-AUC 0.946 on a 357-row, single-region, time-based test
  split is a real, promising result — not external validation, not a
  claim this would perform the same in a different region, season mix, or
  against a differently-sourced landslide inventory. It is a
  **research-grade pilot model**, not a certified hazard product.
- **Even within the pilot area, real gaps remain**: 10 of 42 DEM tiles
  never downloaded (transient network errors — see the pilot's own
  `DataSource.limitations`), and rainfall was extracted only at specific
  historical points/dates, not as a dense grid — so most arbitrary
  coordinate/date queries inside the pilot bbox will still legitimately
  report `rainfall_available: false` unless queried at (or very near) one
  of the 1,848 real extraction points.

## Explainability — two different things, never conflated

- **Risk Factors** (shown on the Risk Analysis page, `risk_factors` in
  API responses): a *local*, rule-based breakdown of the specific
  inputs behind one particular prediction (this zone, right now).
  Computed the same way regardless of whether the ML model or the
  rule-based fallback produced the actual score.
- **Model-Level Feature Importance** (`feature_importance`, present only
  when `prediction_source == "machine_learning"`): the RandomForest's
  *global* `feature_importances_` — describes the trained model as a
  whole, across all of its (synthetic) training data. It is **never** an
  explanation of any single prediction, and the UI/API label it as
  "Model-level feature importance" every place it appears specifically
  so it can't be mistaken for the local explanation above.

## What real ML training required, and what's still open

All four of the following are now done for the pilot area (Phase 20/21):
a real, sufficiently large historical inventory (399 real events after
dropping rows with any missing critical feature); real rainfall/terrain/
land-cover coverage for those events' locations/times; a real negative-
example strategy (buffered, boundary-filtered, terrain-stratified pseudo-
absence sampling — see `app/services/negative_sampling_service.py`); and
time-based splitting with class-imbalance-aware metrics.

Still open, for anyone extending this beyond the pilot:

1. **India-wide (or additional-state) coverage** — needs real DEM/land-
   cover downloads at ~20x this pilot's scale (roughly 841 vs 42 DEM
   tiles for full India) and materially more disk space than this session
   had available (26 GB free; full-India DEM alone is 30+ GB).
2. **Filling the pilot's own real gaps** — retry the 10 DEM tiles that
   failed to download, and consider extracting rainfall on a denser grid
   rather than only at known event/negative points.
3. **A decision on whether/how to wire susceptibility into zone-level
   risk** (`/predict-risk`, alerts) — deliberately not done here; it
   would only be honest for zones inside real-data coverage, and needs
   its own product review before every other zone silently falls back.
4. **External validation** — this model has only ever been evaluated on
   its own held-out time split from the same pilot inventory. A different
   region, a differently-sourced inventory, or real field verification
   would all be needed before calling this more than a research pilot.
